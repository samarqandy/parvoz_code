# PARVOZ CODE — Technical SEO & Conversion Audit

**Property:** https://parvozcode.uz/ · **Repository:** `/home/user/parvoz_code` at commit `62710b4`
**Audit date:** 2026-09-26 · **Method:** static analysis of the repository, unauthenticated `curl` against production, and lab measurement in Chromium (Playwright).

**Rules observed:** no production code was modified. No review, rating, teacher, student, statistic, certification or achievement was invented. Anything that could not be established from the repository or an unauthenticated request is marked **NOT VERIFIED**.

---

## 1. Executive Summary

Parvoz Code is a hand-written static site of 21 indexable pages. Its foundations are unusually clean for a site of this size: every page has exactly one `<h1>`, one self-referential canonical, no heading-level skips, no duplicate titles or descriptions, valid JSON-LD on every page, zero layout shift, and a genuinely good set of six parent-facing articles that answer their title question in the first sentence.

The problems are not in the HTML craft. They are in four places:

**1. The site leaks its own traffic at the conversion step.** The Russian content investment — six translated articles, a Russian hub, a correct hreflang graph — terminates in an Uzbek form. A Russian-speaking parent who lands on `stoimost-kursov-samarkand.html` from search, reads it, and clicks "Записаться на бесплатный урок" arrives at `index.html#yozilish` rendered in **Uzbek**, and the site then writes `parvoz-lang=uz` into their browser so it stays Uzbek. Reproduced in a clean browser profile (§7, §11).

**2. Server-side source code is publicly served.** `/supabase/functions/admin-api/index.ts` returns HTTP 200 with the real source. No credential is hardcoded — every secret is `Deno.env.get()` — but the complete authorisation model, table names, admin user-creation flow and a written README describing which functions run without JWT verification are all readable by anyone (§17).

**3. The trust layer is empty, and the site says so itself.** Zero named teachers, zero photographs, zero reviews. The gallery is four SVG placeholders reading "TEZ ORADA". Meanwhile the site publishes a checklist telling parents that a centre which will not name the teacher is showing "a bad sign", and that dodging the group-size question "is also an answer" — and the site does both (§10, §11).

**4. Measurement is almost entirely absent.** GA4 and Meta Pixel are wired but dormant (empty IDs). Exactly one user action out of ten is tracked. Meanwhile Yandex Metrika's Webvisor is recording full sessions on the page that collects a parent's name, phone number and a child's age, with no field masking anywhere in the repository (§17, §18).

Nothing here requires rewriting the site. The architecture is sound; it is incomplete in specific, addressable ways.

## 3. Critical Findings

### P0-1 — Edge-function and build-tool source is served publicly

```
$ curl -o /dev/null -w "%{http_code} %{size_download}\n" https://parvozcode.uz/supabase/functions/admin-api/index.ts
200 12835
$ curl -o /dev/null -w "%{http_code}\n" https://parvozcode.uz/tools/articles.py
200
$ curl -o /dev/null -w "%{http_code}\n" https://parvozcode.uz/tools/README.md
200
```

Directory listings 404, but individual files are served. `robots.txt` disallows neither path (`grep -i 'supabase\|tools' robots.txt` → no match).

**What is not exposed:** no credential. An exhaustive grep over `supabase/functions/**` for `SERVICE_ROLE|BOT_TOKEN|SECRET|API_KEY|Bearer|password` finds only `Deno.env.get(...)` references — `admin-api/index.ts:4-5,9`, `mark-attendance/index.ts:15-16`, `student-link/index.ts:7-8`, `submit-lead/index.ts:6-7`, `telegram-webhook/index.ts:12-13`.

**What is exposed:** the full server-side authorisation logic of every function, the database table names (`app_config`, `students`, …), the admin user-creation path (`admin-api/index.ts:118-121`, `153-167` — `admin.auth.admin.createUser`, `updateUserById({password})`), and `supabase/functions/README.md`, which is a written description of the security model including which functions run with `verify_jwt` disabled and how the 48-hour parent link token works.

This is information disclosure, not a key leak. It hands an attacker the map without the keys.

Secondary: `.ts` files are served as `content-type: video/mp2t` (Vercel's extension mapping), and `X-Content-Type-Options: nosniff` is absent — mistyped content served without sniff protection.

### P0-2 — `www.parvozcode.uz` is a broken dead end

```
$ getent hosts www.parvozcode.uz
66.33.60.193    cname.vercel-dns.com www.parvozcode.uz
76.76.21.241    cname.vercel-dns.com www.parvozcode.uz

$ curl -sSIL http://www.parvozcode.uz/
HTTP/1.1 308 Permanent Redirect
location: https://www.parvozcode.uz/     ← to itself over TLS, not to the apex
curl: (60) SSL: no alternative certificate subject name matches target host name
*  subject: CN=parvozcode.uz
```

DNS for `www` is live and points at Vercel. Plain HTTP on `www` issues a 308 to HTTPS on `www`. But the certificate covers only the apex — there is no `www` SAN. **Any visitor or crawler that reaches `www` gets a browser TLS interstitial, not a redirect.** Anyone who types the address with `www`, or follows a link or a printed card written that way, sees a security warning instead of the site.

**NOT VERIFIED:** whether the cause is a missing domain in the Vercel project or a failed domain verification. The symptom is verified; the cause is not.

### P0-3 — The Russian conversion path terminates in Uzbek

Reproduced in Chromium with an empty profile, 390 × 844:

| Step | Observed |
|---|---|
| 1. Land on `stoimost-kursov-samarkand.html` | `<h1>` = "Сколько стоят детские курсы в Самарканде?" ✅ |
| 2. Primary CTA | "🎁 Записаться на бесплатный урок" → `index.html#yozilish` |
| 3. After click | URL `index.html#yozilish` |
| 4. Visible `<h1>` | **"Farzandingiz kelajagi bugun boshlanadi"** ❌ |
| 5. Visible form heading | **"Bepul sinov darsiga yozilish"** ❌ |
| 6. `<html lang>` | `uz` |
| 7. `localStorage['parvoz-lang']` | **`uz`** — the visit has now pinned the site to Uzbek for this parent |

Root cause: `index.html:1311` reads `localStorage.getItem('parvoz-lang') \|\| 'uz'`, and none of the seven Russian pages ever writes that key (`grep -c parvoz-lang stati.html` → 0). The Russian pages' navigation also points at Uzbek destinations — `stati.html` nav links resolve to `index.html#kurslar` and the five Uzbek-only course pages.

Every Russian visitor therefore hits an Uzbek wall at exactly the moment they were ready to convert.

### P0-4 — Session recording runs on the page that collects personal data

`index.html:252` (byte-identical on all 21 content pages):

```js

```

`webvisor:true` records the session. `index.html:1072` is the lead form, which collects `full_name`, `phone` (`type="tel"`), and a free-text `note` whose placeholder is "Bolaning yoshi, savollaringiz…" — *the child's age*.

A repository-wide grep for Metrika masking directives — `data-ym-disable-record`, `ym-record-keys`, `ym-hide`, `ym-disable-record` — returns **zero hits** in any `.html` or `.js`. No input carries a masking class.

`maxfiylik.html:92` discloses Yandex Metrika by name but does not mention session recording.

The admin panel, which holds pupil names and parent phone numbers, is clean: no analytics at all, `noindex, nofollow`, and `Disallow`ed.

## 5. Indexability Audit

`robots.txt` contains 17 `User-agent` blocks, **every one byte-identical**: `Allow: /` plus `Disallow: /davomat.html`, then `Sitemap: https://parvozcode.uz/sitemap.xml`. The 16 named-agent blocks are functionally redundant with `*` — zero behavioural effect, but harmless.

| Page | Should index? | robots.txt | meta robots | Verdict |
|---|---|---|---|---|
| 21 content pages | yes | allowed | none (default) | ✅ correct |
| `maxfiylik.html` | yes | allowed | `index, follow` (`:10`) | ✅ (the explicit tag is a no-op) |
| `davomat.html` | **no** | `Disallow` | `noindex, nofollow` (`:6`) | ❌ **self-defeating** |
| 2 verification stubs | ideally no | allowed | none | ⚠️ thin but low-risk; not in sitemap |

**The `davomat.html` defect:** `Disallow` prevents Googlebot from fetching the page, so it can **never read the `noindex`**. A disallowed URL that is linked externally can still be indexed URL-only ("No information is available for this page"). And it *is* linked — `index.html:1242` carries `<a href="davomat.html" … rel="nofollow">`. `rel="nofollow"` does not prevent discovery.

The correct pattern is one or the other, not both: either allow the crawl and let `noindex` do its job, or block it in `robots.txt` and remove the public link.

Canonicals are clean across the board: every page has exactly one, absolute and self-referential, and every one matches its sitemap `<loc>`. No conflicts anywhere.

**NOT VERIFIED:** the actual index state in Google or Yandex. Every claim here comes from `robots.txt`, meta tags and live status codes — not from Search Console or Yandex Webmaster, which were not accessible.

## 6. International SEO Audit

This is the weakest dimension, and the one where the architecture — not the markup — is the constraint.

### What is correct

All seven uz↔ru article pairs are **fully reciprocal and self-referential**. The HTML `<link rel="alternate">` set and the sitemap `xhtml:link` set agree page for page:

```html
<link rel="alternate" hreflang="uz" href="https://parvozcode.uz/bolalar-kurslari-narxi-samarqand.html">
<link rel="alternate" hreflang="ru" href="https://parvozcode.uz/stoimost-kursov-samarkand.html">
<link rel="alternate" hreflang="x-default" href="https://parvozcode.uz/bolalar-kurslari-narxi-samarqand.html">
```

`<html lang>`, `og:locale` and JSON-LD `inLanguage` all agree with each other on every one of the 14 paired pages. The six Russian article pages are the most crawler-friendly content on the site: 100% static Russian prose, `lang="ru"`, with a real `<a href>` cross-language link that works without JavaScript.

### What is broken

**The hreflang graph covers 14 of 21 URLs. The seven highest-value URLs — the homepage, all five course pages, and the privacy page — are outside it entirely.**

For the homepage this is not an oversight that can be patched with tags. hreflang requires **one URL per language version**. `https://parvozcode.uz/` is the only URL for Uzbek, Russian and English:

```html
<h1>
  <span data-lang="uz" class="show">Farzandingiz kelajagi …</span>
  <span data-lang="ru">Будущее вашего ребёнка …</span>
  <span data-lang="en">Your child's future …</span>
</h1>
```
```css
/* assets/site.css:987-989 */
[data-lang] { display:none; }
[data-lang].show { display:inline; }
```

Consequences, precisely:

1. **Only Uzbek is primary text.** In the served HTML, `class="show"` is hardcoded on the `uz` spans only. The 180 Russian and 180 English spans are `display:none`.
2. **The ru/en copy is in the DOM but CSS-hidden** — ~21 KB, 23% of the HTML. Google will parse it and, consistent with its long-standing treatment of hidden text, heavily discount it. It is crawled but cannot rank.
3. **`<html lang="uz">` is what is served.** `document.documentElement.lang = lang` at `index.html:1303` runs client-side only. Yandex, which leans harder on the declared page language, sees an Uzbek page — in a city where Russian is a major query language.
4. **Language choice lives in `localStorage`** — no cookie, no server signal, no `Vary: Accept-Language`. Every crawler visit starts fresh on Uzbek.

**The five course pages are Uzbek-only** — zero `data-lang` spans, zero language switcher. A visitor who sets RU on the homepage and clicks through to `/robototexnika-kurslari.html` gets a monolingual Uzbek page with no way back. What those pages *do* carry is a single visible Russian paragraph:

```html
<!-- dasturlash-kurslari.html:342 -->
<div class="ru-block" data-reveal>
  <h2>🇷🇺 Курсы программирования для детей в Самарканде</h2>
  <p>Учебный центр Parvoz приглашает детей от 6 лет … 300 000 сум в месяц, первый урок бесплатно.</p>
</div>
```

It is not hidden (`assets/site.css:1070` has no `display:none`) and carries **no `lang` attribute** — an undeclared Russian island inside a document declared `lang="uz"`, targeting exactly the query a Russian-speaking parent would use, on a URL that can never be hreflang'd for Russian.

**The homepage links to zero Russian pages.** `grep -c 'href="stati.html"' index.html` → **0**. The only article-hub link on the homepage is `index.html:1020` → `maqolalar.html`. The entire seven-page Russian cluster is reachable from the homepage only indirectly, two clicks deep, via the Uzbek hub.

**`x-default` points at the Uzbek version** on all 14 paired pages. Defensible — with no language-selector page, nominating the default-language version is the common pragmatic choice and Google accepts it — but it is absent from the six URLs a locale-unmatched visitor is most likely to hit.

### English

English exists on `index.html` only — roughly 8% of the HTML, present nowhere else on the site. It cannot rank (hidden, no URL), it cannot be hreflang'd, and it sends a partial-translation signal. Per the decision recorded in §20, it should be removed.

### What does not exist

### Recommended architecture

**Keep flat URLs. Do not migrate to `/courses/…`.**

Splitting them creates two thin pages competing with `dasturlash-kurslari.html` and with `scratch-yoki-python.html`, which already answers that question well. Every one of the 21 JSON-LD blocks parses cleanly. Coverage is broad: `EducationalOrganization` + `LocalBusiness`, `WebSite`, `Course`, `CourseInstance`, `Offer`, `FAQPage`, `BreadcrumbList`, `Article`, `CollectionPage`, `ItemList`.

**Defect — the schedule contradicts the product and itself:**

```json
"courseSchedule": {                            // dasturlash-kurslari.html:100
  "repeatFrequency": "P1W",
  "repeatCount": 3,
  "byDay": ["Monday","Tuesday","Wednesday","Thursday","Friday","Saturday"],
  "startTime": "10:00",
  "endTime": "18:00"
}
```

This declares a single 8-hour block on all six days. ### FAQPage

18 pages carry `FAQPage`. Every question and answer was string-compared against the visible DOM after unescaping entities and stripping tags. **17 of 18 match character for character.** The one exception is the homepage answer documented as P0-5.

### Article

All 12: `headline` matches `<h1>` exactly, `description` matches the meta, `url` matches the canonical, `inLanguage` matches `<html lang>`.

Missing on all 12: `image`, and `publisher.logo`. `author` and `publisher` are byte-identical organisation objects — and `author` is an organisation because **no human exists to name**.

All 12 share `datePublished == dateModified == 2026-09-25`. Freshness cannot differentiate them, and once any article is genuinely revised, `dateModified` must move or the signal becomes actively misleading.

### Recommended JSON-LD architecture

```
index.html
  #organization  (EducationalOrganization + LocalBusiness — full NAP, geo, hours, sameAs, logo)
  #website       (WebSite → publisher: {@id: #organization})

every other page
  WebPage        (→ isPartOf: {@id: #website})
  <page entity>  (Course / Article / CollectionPage)
       provider / author / publisher: {@id: "https://parvozcode.uz/#organization"}
  BreadcrumbList
  FAQPage        (only where answers are visible verbatim)
```

The rule: **declare the organisation once, reference it everywhere by `@id`.** Add `WebPage` as the top-level node on every page (currently absent everywhere). Consider `WebSite.potentialAction` → `SearchAction` only if site search is ever built — not now.

Do **not** add `AggregateRating` until real reviews exist.

## 18. AI Search / AEO Audit

### Strengths — this is the site's best dimension after content

`robots.txt` explicitly allows 14 AI agents by name (GPTBot, OAI-SearchBot, ChatGPT-User, ClaudeBot, Claude-SearchBot, Claude-User, PerplexityBot, Perplexity-User, Google-Extended, Applebot-Extended, Amazonbot, meta-externalagent, cohere-ai) plus Googlebot, YandexBot and Bingbot. Nothing is blocked except the admin panel. `CCBot` and `YandexAdditional` are not named but are allowed via the wildcard — no behavioural difference.

`llms.txt` (5 142 B) is a hand-maintained fact sheet: NAP, hours, group times, price, ages, 8 Q&As, and both article indexes. Checked field by field against ground truth, **every NAP fact matches**.

Ten of twelve articles answer their title question in the first sentence (§10) — the single most extractable content pattern.

Organisation attribution exists on every article via `author` and `publisher`.

### Gaps

1. **No human to cite.** Zero `Person` nodes, zero bylines, zero staff names, zero `CourseInstance.instructor`. Answer engines weight identifiable expertise; there is none to weight.
2. **`llms.txt` is not referenced anywhere** — not from any HTML `<link>`, not from `robots.txt`, not from `sitemap.xml`.
3. **`llms.txt` drifts from the site** on lesson language (§10) and carries 8 FAQs where the homepage carries 5, paraphrased rather than verbatim. Divergence between the fact sheet and the pages is exactly what erodes an answer engine's confidence.
4. **The first `<p>` on every article is the date line**, not the answer:
   ```html
   <p class="doc-date">Yangilangan: 2026-09-25 · <a class="art-lang" …>🇷🇺 Читать по-русски</a></p>
   <p class="art-lede"><strong>The actual answer.</strong> …</p>
   ```
   A naive first-paragraph extractor gets the date. Moving the metadata after the lede, or marking the lede with `data-answer`, removes that risk.
5. **The entity is fragmented** — 29 anonymous organisation nodes instead of one `@id`-linked entity (§14).
6. **Russian pages carry no country signal.** No Russian page contains "Узбекистан", and none carries address schema — while "Самарканд" collides with "Самара" in Russian-language results (§7).

### Recommendations

- Reference the organisation by `@id` from every page.
- Add `Person` nodes and `instructor` once a teacher can be named.
- Put a `LocalBusiness` or organisation node with the full address on the Russian pages, and write "Самарканд, Узбекистан" in the Russian prose at least once per page.
- Link `llms.txt` from `robots.txt` and from a `<link rel="alternate" type="text/plain">`.
- Reconcile the two `llms.txt` contradictions and make its FAQs verbatim copies of the on-page ones.
- Move the date line below the lede on article pages.

## 20. Recommended Architecture

Based on the decisions recorded with the owner: **add Russian course pages** (not a full `/ru/` namespace), and **remove English**.

### URL structure

```
/                                  uz homepage        ←→  /ru.html
/ru.html                           ru homepage        ←→  /
/dasturlash-kurslari.html          uz                 ←→  /kursy-programmirovaniya.html
/robototexnika-kurslari.html       uz                 ←→  /robototehnika.html
/matematika-kurslari.html          uz                 ←→  /matematika.html
/shaxmat-kurslari.html             uz                 ←→  /shahmaty.html
/ingliz-tili-kurslari.html         uz                 ←→  /angliyskiy.html
/maqolalar.html + 6 articles       uz                 ←→  /stati.html + 6   (already correct)
/maxfiylik.html                    uz                 ←→  /konfidencialnost.html
```

**Why flat URLs, not `/ru/`:** every page references its assets relatively (`assets/site.css`, `manifest.json`, `favicon.png`). A directory level would require rewriting every one of those paths on every page, for no ranking benefit — `hreflang` and `<html lang>` carry the language signal, not the path. The six Russian articles already work exactly this way.

### The three changes that matter

**1. Split the Russian homepage out of `index.html`.**

This is the only way to close P0-3, and it fixes four problems at once: the Russian CTA lands on a Russian page; `index.html` becomes genuinely `lang="uz"` and can finally carry `hreflang`; the hidden Russian markup (21 KB) stops shipping to every Uzbek visitor; and the `data-lang` machinery can be deleted from the homepage.

**2. Turn each `.ru-block` into a real Russian course page.**

The Russian paragraph at `*-kurslari.html:342` already targets the right query — it just sits on a URL that can never rank for it. Promote it to a full page with its own `Course` schema, its own FAQ and reciprocal hreflang, and delete the block from the Uzbek page.

**3. Remove English.**

Roughly 8% of `index.html`, present nowhere else, unable to rank. Parents in Samarkand search in Uzbek and Russian.

### `vercel.json` — currently absent

One file closes P0-1, P0-2, P1-6, P1-7 and P1-18:

```jsonc
{
  "headers": [
    { "source": "/(.*)", "headers": [
      { "key": "X-Content-Type-Options", "value": "nosniff" },
      { "key": "X-Frame-Options",        "value": "SAMEORIGIN" },
      { "key": "Referrer-Policy",        "value": "strict-origin-when-cross-origin" },
      { "key": "Strict-Transport-Security", "value": "max-age=63072000; includeSubDomains" }
    ]},
    { "source": "/assets/(.*)", "headers": [
      { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
    ]}
  ],
  "redirects": [
    { "source": "/:path*.html/", "destination": "/:path*.html", "permanent": true }
  ],
  "rewrites": [
    { "source": "/supabase/(.*)", "destination": "/404.html" },
    { "source": "/tools/(.*)",    "destination": "/404.html" }
  ]
}
```

Plus a branded `404.html`. Note that the long `immutable` cache is only safe once asset filenames are versioned — until then use a shorter `max-age` on `assets/`.

The `www` certificate is fixed in the Vercel dashboard, not in the repository: add `www.parvozcode.uz` as a domain and set it to redirect to the apex.

### What NOT to change

- **Do not migrate to `/courses/…`.** Cost without benefit (§9).
- **Do not adopt a framework.** The site is fast because it is static. Nothing in this audit is caused by the lack of a build step, and `tools/gen_articles.py` already handles the repetitive pages.
- **Do not split Scratch and Python into separate pages.** They are modules, not products (§9).
- **Do not add rating markup** until real reviews exist.
- **Do not add a fourth language.**

### The honest summary

This is a well-built small site with two kinds of gap.

The first kind is configuration: a missing `vercel.json`, an unclaimed domain alias, a stale sitemap. These are hours of work with immediate, verifiable results, and they include the most serious finding in the audit — server source code served to anyone who asks.

The second kind is harder, and no amount of markup will fix it. The site asks parents to hand over their child, and shows them no teacher, no classroom, no student and no review. It even tells them, in its own words, that a centre which does this is showing a bad sign. Until a real name, a real photograph and a real review appear on these pages, the technical work has a ceiling — and it is lower than the quality of the underlying site deserves.
